蛋白钱包 ProteinWallet

面向大学生的 AI 饮食记账工具 · 个人项目，产品设计与开发 · 2026.07 — 至今 · 线上产品 · GitHub

拍一张餐食或小票，同时记账与记营养。给生活费有限、想增肌的在校大学生回答一个问题：每一美元换到了多少克蛋白质。v1 做美国校园（美元 + 美国连锁 + 芝大食堂），国内校园版在路线图上。

3 级估算：连锁官方表 → 食堂菜品库 → 模型目测
640 道食堂官方菜品库（芝大 4 个食堂）
17/17 · 4/4评测区间命中（连锁 / 食堂）

背景与痛点

在校大学生生活费有限，又是健身、增肌最集中的人群。一天中大部分正餐发生在食堂、连锁快餐和外卖，根本无法称重，传统营养 App 的"精确到克"从第一步就做不到；自己做饭的同学同样算不清一盘家常菜。另一边，营养 App 不管钱，记账 App 不管营养，而这群人真正的决策是两者的交点：这顿饭的蛋白质值不值这个价。

竞品对比：MyFitnessPal、Keep 等为"自己做饭、能称重"的用户设计，条目搜索加手动克数在食堂外卖场景摩擦极高，且不管钱；记账 App 只管钱。切口是场景（无法称重的餐食）× 约束（预算），这是它们的盲区。

产品把"记一顿饭"压缩成一个动作：拍小票。小票同时包含金额和菜品，一次识别就完成记账与记餐。

定位调整：从"留学生"到"生活费有限的大学生"

第一版写的目标用户是"在美留学生"，后来改为更准的画像"生活费有限、想增肌的在校大学生"，生活费有限正是他们增肌食物选择受限的根源。PRD、文案、prompt 一起改：v1 做美国校园（美元、美国连锁、芝大食堂），国内校园版进路线图，货币先解耦（美元 / 人民币，不做汇率换算，一个用户只用一种货币，换算反而引入假精确）。

定位改了之后，最高频场景变成食堂，而食堂恰好是纯目测最差的一档。这直接推出了下面的第二级数据源。

核心指标与设计哲学

蛋白质单价（¢/g protein）：用户吃过的每样食物，一克蛋白质花多少美分。这是全产品唯一的自创指标，也是传播点：食堂烤鸡胸约 1.2¢/g，Chipotle 鸡肉碗约 2.8¢/g，某中餐外卖约 5.5¢/g，一眼看出钱该花在哪。周报里展示用户个人的"蛋白质单价排行榜"。

诚实的模糊。所有营养估算一律输出"区间 + 置信度 + 估算依据"，永不假装精确。有官方营养数据的连锁餐窄区间、高置信度，标注"来自官方营养表"；食堂和中餐等无官方数据的餐食宽区间、中低置信度，标注"视觉估算"。区间和置信度始终显示在一级界面，不藏在二级页。市面产品"精确到个位卡路里"是假精确，这个产品反向设计。

范围取舍：明确不做的事

每一条都是主动决策，不是没来得及做。

不做什么理由
超市菜价爬虫、实时价格追踪爬虫脆弱且可能违反网站条款；自炊花销已由"买菜小票拍照"覆盖
按食材精确累加自炊营养回到"称重"老路，摩擦杀死记录；自炊统一走成品拍照目测，宽区间低置信度
推荐"你该吃什么"饮食推荐碰营养学专业责任，幻觉风险高且无资质背书；只做"现状 + 差额"，决策权留给用户
热量上限警告、激进减重目标、评判性文案营养追踪产品有把用户推向过度节食的风险，在设计层主动规避，这是产品的伦理边界
假精确的单一数值与"诚实的模糊"冲突
微量营养素、脂肪与碳水细分v1 只追热量和蛋白质，聚焦增肌与预算两个核心诉求
社交、排行榜、好友比较v1 是单人工具，先跑通个人闭环

面试里最常被问的一条是"为什么砍掉饮食推荐，那不是更有用吗"。回答是：更有用，但风险不对称。推荐错了责任在产品，信息错了用户还能自己判断；在没有营养学背书的前提下，"告知现状"和"指导行为"是两个风险量级。

三级估算方案

  1. 先匹配连锁官方数据。识别出连锁品牌时优先用内置官方营养表。17 家连锁里只有逐行核对过官网的 5 家（Chipotle、麦当劳、Shake Shack、Sweetgreen、KFC）能标"官方数据"+ 高置信度；3 家抽查过、9 家凭记忆录入的一律降级为"参考数据 · 未核实"+ 中置信度，直到核实为止。
  2. 再匹配学校食堂官方菜品库。芝大 4 个食堂（Baker / Bartlett / Woodlawn / Cathey）的菜单由 Dine On Campus 公开，每道菜有份量、热量、蛋白质，整理成 640 道菜的菜品库进仓库。用户选一个食堂，模型只判断"盘子里是库里哪几道、各几份"，算术由代码按官方每份数据完成；菜名是官方的、份数是目测的，所以标"食堂菜单"+ 中置信度，区间 ±20%。Dine On Campus 覆盖全美几百所学校，换学校只换数据文件。
  3. 都匹配不上才让模型目测。宽区间，强制低置信度。

数据层的取舍：该站接口对服务器和其他域名封死，所以和连锁表一样做仓库内快照、手动刷新；"哪天哪个档口有什么菜"的列表拿不到，就只做菜品库而不是每日菜单；同名同份量但做法不同的菜（Scrambled Eggs 210 vs 100 kcal）合并成一个范围条目，这正是"诚实的模糊"的落地。

模型只做识别，所有算术交给代码，这是抑制幻觉的主要手段。

输出格式

Prompt 要求模型只返回固定字段的 JSON，由 zod 校验后才进入界面：

{
  "meal_name": "鸡肉碗",
  "merchant": "Chipotle",
  "amount_usd": 11.5,
  "kcal_low": 650, "kcal_high": 800,
  "protein_low_g": 45, "protein_high_g": 55,
  "confidence": "high",
  "basis": "Chipotle 官方营养表，按识别出的配料组合估算",
  "source": "official_table"
}

Prompt 设计要点

  • 宁宽勿窄：区间宽度与置信度挂钩，禁止输出单点值。
  • 禁止猜测金额：照片里没有价格时金额返回空，由用户补充。
  • 多菜品小票返回数组，每项单独估算。
  • 识别不出食物时返回明确的错误字段，前端引导重拍，绝不编造。

不确定性的界面表达

高置信度用实线边框加"官方数据"标签；中低置信度用虚线边框加"参考数据"或"目测估算"标签。区间始终显示两端，不显示单一均值。2026-10 又加了一层：模型每道菜多返回"按几勺 / 几块估的、有没有把握"，没把握时整块标黄，确认卡上一排一键按钮（×0.5 / 1 / 1.5 / 2）按比例重算。拍照估热量的误差大头在份量不在认菜，让用户点一下份量是最便宜的准确率提升。

评测体系

真值来自连锁餐厅公开的官方营养数据，零成本、可验证。四项指标和目标在写功能代码之前定下：

指标定义目标
区间命中率真实值落在输出区间内的比例蛋白质 ≥ 85%
区间相对宽度（上限 − 下限）/ 中点，衡量区间是否宽到没用高置信度条目 ≤ 30%
小票解析准确率金额、商家、菜品数全对的小票比例≥ 90%
用户修正率确认卡片被手动修改的记录占比，线上持续监控趋势下降
关键权衡：命中率和宽度天然对抗。区间拉到无穷大，命中率 100% 但毫无用处。调 prompt 的过程就是在这条权衡曲线上找位置，每轮同时记两个数字。

第二轮（2026-10-28，prompt v2，食堂集）

4 条食堂文字样本以菜品库为真值：第一次 3/4，漏的是两条同名同份量的 Scrambled Eggs（210 vs 100 kcal）模型选了另一条；把同名同份量菜品合并成范围条目后 4/4。评测集里真实照片目前是 0 张，先列了 30 张照片的拍摄清单（12 连锁 / 12 食堂 / 6 辅助），拍照准确率要先测量再决定是否动模型。

100 个用户画像的模拟测评

在种子用户到位之前，用 100 个用户画像（大一新生、交换生、健身初学者、素食者、过敏人群、预算紧张的增肌学生、隐私敏感者等）对线上版本做了一轮模拟测评：每个画像走一个具体场景，按 10 个维度打分并给出一条改进建议和优先级。均分 3.68 / 5，61% 打 4 分以上；5 项 P0、51 项 P1。

维度均分维度均分
预算与餐食性价比3.90小票、花销与消费场景3.60

最集中的诉求：36% 的反馈要求估算结果可逐项确认、可修正、标明范围与依据，对应已上线的确认卡、份量一键追问和记录可编辑；15% 希望重复餐一键复用，对应"再来一份"。5 项 P0 集中在两件事：照片与小票的存储、删除规则和隐私声明；数据导出与备份。这两项排入下一版。

数据指标与埋点

  • 北极星指标：每用户每周记录餐次，目标 ≥ 10，即大部分正餐都记了。
  • 留存：第二周还在记录的用户数。
  • 记录摩擦：从打开到保存的中位耗时，目标 ≤ 15 秒。
  • 埋点实现：v1 不接分析 SDK，记录开始、完成、修正和页面打开等事件写入本地事件表，随 JSON 导出一起收集。
